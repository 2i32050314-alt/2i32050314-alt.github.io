Base64 的三个误解：它不是加密，还会让体积变大

2026-11-08　·　Demo_Li

Base64 被用得太多，以至于不少地方把它当成「编码一下更安全」的手段。它解决的是另一个问题：让二进制数据能安全穿过只接受文本的通道。

误解一：Base64 是加密

不是。Base64 是一张固定的对照表，把每 3 个字节切成 4 个 6 位，每个 6 位映射成 64 个可打印字符之一，不足 3 字节的用 = 补齐。

任何人都能还原，不需要密钥。所以把密码、token 用 Base64 包一层等于没有保护，只是看起来不像明文。

它真正解决的问题是：HTTP 头、JSON 字符串、CSS 里不能直接放任意字节。比如把图标塞进样式表：

.icon { background-image: url("data:image/png;base64,iVBORw0KGgo..."); }

误解二：中文直接 btoa 就能转

浏览器里 btoa() 只接受 Latin-1 范围内的字符，遇到中文会抛 InvalidCharacterError。

正确顺序是先把字符串按 UTF-8 编成字节，再对字节做 Base64：

const bytes = new TextEncoder().encode("中文");
const b64 = btoa(String.fromCharCode(...bytes));

解码则相反，先 atob 得到字节，再用 TextDecoder("utf-8") 还原。少了这一步，中文就会变成乱码或者直接报错。这是「Base64 中文乱码」最常见的来源。本工具内置了这两步，所以中文和 emoji 都不会出问题。

误解三：Base64 只变大一点点

每 3 字节变 4 字符，体积增加约 33%。如果原数据本身接近随机（压缩过的图片、加密后的密文），那就是实打实的增长。

两个场景要特别注意：

  • 不要把已经压缩过的图片转 Base64 内联进 HTML。图片可能因此更大，而且无法被单独缓存，每次访问都要随页面传输。
  • 不要把超过几十 KB 的二进制塞进 URL 或 Cookie。两者都有硬性长度限制。

URL 里要换另一套字符表

标准 Base64 里的 + 和 / 在 URL 里有特殊含义，直接拼进去会坏。所以有 Base64URL 变体：把 + 换成 -、/ 换成 _，并去掉结尾的 =。

JWT 用的就是 Base64URL。这也是为什么有些 JWT 的 payload 段看着像 Base64，用标准 Base64 解码却失败。

怎么快速判断一段乱码是不是 Base64

字符集只包含 A-Za-z0-9+/=，长度是 4 的倍数，末尾可能有 1 到 2 个等号。满足这几条基本就是。反过来，如果出现了 - 和 _ 而没有 + /，多半是 Base64URL。
