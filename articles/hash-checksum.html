哈希校验怎么用才不算白做

2026-11-08　·　Demo_Li

下载页面上挂着一行 SHA-256，很多人扫一眼就算「验证过了」。真正的校验要自己做一遍，而且要和对的地方比。

校验文件完整性

服务端发布文件时给出哈希，你下载完成后在本机算一遍，两个值一样才说明文件完整且未被篡改。

这一步能挡住两类问题：传输中断导致的文件损坏，以及被中间人替换过的安装包。它挡不住的是「服务端本身就给了错的文件」——那时候你比对的哈希也是错的，两边一致反而更安心，这是哈希校验的边界。

算法怎么选

  • SHA-256：默认选它。够安全，浏览器原生支持，速度快。
  • SHA-1：已被证明可以构造碰撞，只用于兼容老系统，别用于安全场景。
  • SHA-384 / SHA-512：输出更长，安全裕度更高，速度略慢。
  • MD5：只适合判断文件是否相同这类非对抗场景。绝对不能用来校验下载包的完整性。

「构造碰撞」的意思是攻击者可以造出两个内容不同但哈希相同的文件。SHA-1 现在能做到这件事，成本已经不高。

哈希不是加密

哈希是单向的，理论上不可逆。但简单文本（比如常见密码）的哈希可以被彩虹表直接反查——因为候选空间太小，预先算好一张表就能查。

所以密码存储不能用 SHA-256 裸哈希，要用加盐加慢哈希（bcrypt、scrypt、Argon2）。盐让每个用户的哈希唯一，彩虹表失效；慢哈希让每次尝试的代价变高，暴力破解变贵。这三件事缺一不可。

一个常见的差异来源

同样一段文字，两个人算出来的哈希不一样，最常见的原因是换行符和编码：

  • Windows 的 CRLF 与 Unix 的 LF 差一个字节，哈希完全不同；
  • 文件末尾多一个换行；
  • 文本编码不同（UTF-8 与 UTF-8 with BOM）。

比对配置文件的哈希时，先统一换行符，否则会得到「内容一样但哈希不同」的假警报。

实现上的注意点

浏览器原生的 WebCrypto 只在 HTTPS 或 localhost 下可用。用 file:// 直接打开本地 HTML 会拿不到 crypto.subtle，表现是 undefined 而不是报错，容易误判成代码写错。

本工具的哈希功能就走 WebCrypto，所以你在这页面上能算出结果，说明环境是正常的。
