CSV 用 Excel 打开是乱码，问题出在 BOM

2026-11-08　·　Demo_Li

从系统导出的 CSV，用 Excel 打开中文全变成乱码，用文本编辑器打开又是正常的。这不是文件坏了，是编码和 BOM 的问题。

一、编码：UTF-8 还是 GBK

Excel 在中文 Windows 上打开 CSV 时，默认按系统代码页（GBK/936）解释，不按 UTF-8。文件是 UTF-8 存的，Excel 用 GBK 去读，中文自然就散了。

三个解法，按可靠性排序：

  1. 加 BOM。在文件开头写入三个字节 EF BB BF，Excel 看到就会按 UTF-8 解释。兼容性最好，代价是被其他程序读取时，第一个字段名前面会多一个看不见的字符。
  2. 导出成 GBK。老系统常用，缺点是非中文环境打开还是乱码。
  3. 用「数据 → 从文本/CSV」导入，手动指定编码为 UTF-8。最规范，但要多点几步。

二、BOM 带来的连锁问题

加了 BOM 之后，用代码读文件会踩坑：

const rows = csv.split("\n");
const header = rows[0].split(","); // 第一个字段名前面其实是 BOM

于是用字段名取值会拿到 undefined，而打印键名看着完全正常，因为 BOM 是不可见字符。这类问题很难从输出里看出来。

处理办法是读取后立刻剥掉：

const text = raw.replace(/^\uFEFF/, "");

本工具的 CSV 转 JSON 会自动做这一步，所以带 BOM 的文件也能正确取出表头。

三、字段里有逗号、引号和换行

CSV 不是「用逗号分隔」这么简单。按 RFC 4180，字段可以包含逗号、换行，前提是用双引号包起来；字段内部的引号写成两个双引号。

name,note
张三,"会说，也会写"
李四,"他说""这条要改""，然后就走了"

如果解析只是按逗号切分，这两种情况都会错位，而且错位之后整行的列都往后偏，看起来像数据本身有问题。用标准解析器，或者至少处理引号状态机。

四、数字被 Excel 吃掉

比乱码更隐蔽的问题是：超过 11 位的数字（手机号、订单号）在 Excel 里会被转成科学计数法，15 位以上直接丢精度，变成一串 0。

CSV 里没法声明这一列是文本，Excel 也不认。可行的办法是在数字前加制表符或单引号让它变成文本，或者干脆不交给 Excel 处理。

这类问题在数据交付时经常被忽略：你发出去的文件看起来没问题，对方打开后订单号全变了，然后来找你。
